# BUG-20261011-006 · V2: «Голос ИИ идёт рывками (дерганый звук)»

- **Статус:** исправлено
- **Область:** `services/api/internal/voiceorchestrator/orchestrator.go` (`PaceFrames`)

## Симптом
Когда ИИ говорит (TTS), звук воспроизводится рывками, прерывисто (обрывы/паузы).

## Корень (аргументация)
TTS-кадр = 250 мс аудио (`ChunkBytes=8000` = 4000 сэмплов @16 кГц). `PaceFrames` шлёт
кадры **just-in-time**: `nextSend = now.Add(FrameDur)` (250 мс), т.е. **темп отправки ≈
темп воспроизведения** (250 мс аудио / 250 мс), **без задела** (пре-буфера). Клиент
(`PcmPlayer`) ставит кадры в AudioContext вплотную и начинает на первом кадре (тест
`player.test.ts` требует start на первом кадре) — у клиента **почти нет буфера**.

Две причины underrun-а (буфер клиента пустеет раньше, чем придёт следующий кадр):
1. **Дрейф pacing**: тик pacing-а — тикер 25 мс; отправка происходит на первом тике
   после `nextSend`, т.е. интервал = 250 мс + (0..25 мс), в среднем ≈262 мс. Сервер
   отдаёт аудио **медленнее реального времени**, а клиент играет точно в реальном →
   буфер невосполнимо стекается → через ~N кадров — обрыв.
2. **Джиттер** (сеть/планировщик/паузы между TTS-запросами по фразам): любой сбой
   just-in-time ритма сразу даёт тишину, т.к. задела нет.

(Путь хода кандидата `StreamCandidateTurn` → `ProduceOrderedTTS` (пул из 3) + `PaceFrames`;
`StreamAIAudio` (greeting/подсказка) — по предложениям последовательно, та же проблема.)

## Фикс
**Пре-буфер** в `PaceFrames`: первый кадр отправляем только когда в очереди накоплено
`≥ preBufferFrames (2 кадра = 500 мс)` (или при окончании потока), дальше — по
pacing-ритму. Клиенту даётся **задел 500 мс**: он поглощает дреф pacing и джиттер —
underrun больше не возникает, звук идёт плавно. Изменение точечное (одно условие отправки
в `PaceFrames`), число кадров/seq/длина не меняются; бarge-in/end-кадр не затронуты.

Задержка старта речи +до ~500 мс (задел) — допустимая цена плавности (локальная сессия,
TTS первого предложения готов быстро).

Регресс: api `go test ./...` зелёный (orchestrator_test: ≥2 кадра, seq 0,1,2…, бarge-in <10).
Тесты не менялись. Клиент (`PcmPlayer`) не трогали — start на первом кадре сохранён
(player.test.ts зелёный).
