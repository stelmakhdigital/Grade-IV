# BUG-20261011-011 · M5: по «Отправить» уходит только хвост сообщения

- **Статус:** исправлено
- **Область:** `services/api/internal/httpapi/voice_pipeline.go` (`handleSTTStreamFinal`)

## Симптом
В режиме записи кандидат видит в окне записи ВЕСЬ надиктованный текст, но по «Отправить»
(кнопка, не голос) в диалог уходит только его **хвост** (концевая часть).

## Шаги / корень (связь с обработкой STT-final, зона BUG-005)
1. Кандидат диктует ответ в режиме записи. Начало диктовки часто ложится, **пока ИИ ещё
   говорит** (`ttsActive` — ИИ договаривает вопрос).
2. `handleSTTStreamFinal` на входе в barge-in-ветку:
   `if w.ttsActive.Load() { if !sttBarged && ms < BargeInMinSpeechMS { return } ... }`.
   Короткие начальные фразы (< `BargeInMinSpeechMS`, ~500 мс — Silero-оценка фразы)
   **отбрасывались** («защита от эха/дыхания») — и в режиме записи тоже, т.к. проверка
   шла ДО разветвления recording/voice.
3. Утеряны **начальные** сегменты диктовки (пока `ttsActive`, до первого barge-in);
   после конца TTS сегменты идут. Итог: накопленный (видимый) транскрипт короче реально
   сказанного, а при отправке `mergeRecording(recSegs, partial)` уходит то, что
   накопилось = **хвост**. Клиентский `mergeRecording` корректен (склеивает ВСЕ segs+partial)
   — корень на сервере (дроп final-ов в recording-ветке).

## Фикс
В режиме записи **все** non-empty final-ы кандидата идут в транскрипт
(`emitRecSegment`) — **до** barge-in-гейта: barge-in-шорт-фраза-дроп и `stopTTS` на
короткой реплике — это voice-путь (анти-эхо); в записи они теряли начало диктовки.
Сохранён guard стадии/статуса (voice+active). Теперь видимый транскрипт == отправленный.

Регресс: api `go test` (voice_pipeline/vad_stream/barge-in) — зелёный; FE 114 — зелёный.
