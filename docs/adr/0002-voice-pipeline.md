# ADR-002. Голосовой конвейер: VAD + utterance-STT + streaming-LLM + phrase-TTS

**Статус:** принято (2026-09-09)

## Контекст
Живой диалог на русском (FR-V1…V8). Бюджет: конец реплики кандидата → начало аудио ИИ
p50 < 2,5 с, p95 < 4 с (FR-V4). Заполнение пауз > 8 с (FR-V6). Деградация в текстовый режим
при падении STT/TTS (FR-V8). Провайдеры self-hosted, подменяемые (решения #13, #16).

## Решение
1. **VAD** — Silero VAD (модель входит в пакет `silero`) на сервере, поверх входящего PCM-потока.
   Окончание реплики — тишина ≥ 900 мс (`VAD_END_SILENCE_MS`, допуск 700–1200).
2. **STT** — faster-whisper, модель из конфига `STT_MODEL`:
   prod — `large-v3-russian` (GPU); локальная dev — `small` (16 GB RAM / 11 GB disk).
   Распознавание **по реплике** (utterance-based), не токеновый стриминг: в ходовом режиме
   частичные гипотезы не нужны, а faster-whisper даёт real-time на GPU и ~real-time на CPU
   для `small`. `POST /api/v1/stt` (аудио-реплика → `{text, confidence, duration_s}`).
3. **LLM** — OpenAI-совместимый streaming-клиент (см. ADR-005). Инженер интервьюера (api):
   системный промпт = персона + программа грейда/стека + транскрипт сессии + текущая стадия +
   скрытый рубрикатор; ответ **стримится по токенам**, режется по предложениям и
   посылается в TTS фразами (первое предложение — сразу).
4. **TTS** — Silero v5 (MIT), `POST /api/v1/tts` (`{text, speaker}` → стрим PCM16 16 кГц,
   чанкованный ответ). Спикер из конфига; выразительность (интонации) — подбором спикера
   и пунктуацией/эмо-подсказок в промпте LLM.
5. **Заполнение пауз** — таймер оркестратора: в стадии voice тишина кандидата > 8 с
   (`SILENCE_NUDGE_S`) → служебный «nudge»-ход LLM («всё понятно? расскажите ещё…»).
6. **Деградация** — voice-сервис недоступен (health-check) → сессия переходит в текстовый
   режим (FR-V8): кандидат пишет, ИИ отвечает текстом; событие фиксируется в истории.

## Latency-бюджет
| Этап | Prod (GPU) | Локально (M2, small/4B) |
|---|---|---|
| VAD (конец реплики) | 0.9 с | 0.9 с |
| STT (utterance) | ≤ 1.0 с | 1.5–3 с |
| LLM (TTFB до первого предложения) | ≤ 0.7 с | 1–2 с |
| TTS (первый чанк) | ≤ 0.3 с | ≤ 0.5 с |
| **Итого (конец → начало аудио ИИ)** | **p50 ≈ 2.5–3 с** | **p50 ≈ 4–6 с** |

Целевые p50/p95 (FR-V4) достигаются в prod-конфигурации; локальные значения — допуск dev.

## Альтернативы
- **Токеновый/чанковый streaming STT** (whisper-streaming, chunk-ASR): сложнее (оверлап,
  калибровка чанков), выигрывает <0.5 с — не критично в ходовом режиме. Апгрейд — фаза Operations.
- **WebRTC-аудио**: см. ADR-001.
- **Коммерческие TTS (gpt-4o-mini-tts и др.)**: отклонены — только self-hosted (решение #16).

## Последствия
- + Абстракция `STTProvider`/`TTSProvider` + стабильные `/api/v1/stt|tts` — провайдеры
  подменяются без изменения конвейера (решение #16).
- + Упрощённый протокол (реплики, не токены) — предсказуемый WS-трафик.
- − Чувствительность к долгим паузам внутри реплики (кандидат «задумался» > 0.9 с) —
  смягчение: настраиваемый VAD-порог + nudge; при необходимости апгрейд streaming STT.
- − Silero v5 естественнее коммерческих TTS слабее — мониторинг качества (отзывы, A/B
  спикеров) в Operations; замена TTS-провайдера — только конфигом.

## Поправка (2026-10-08) — clause-level диспетчизация TTS

**Статус:** реализовано (T-20261008185701)

**Мотив.** В живом голосовом диалоге разрывы между фразами реплики ИИ составляли
750–1500 мс: предложение уходило на TTS только целиком сгенерированным, узкое место —
скорость токенов LLM-стрима (решение #36). Синтез TTS — не bottleneck (~89 мс на
предложение; отчёт замеров — docs/test-results/tts-clause-dispatch-2026-10-08.md).

**Механизм.**
1. **Клиузы.** Предложение ответа LLM дополнительно (помимо разбиения на предложения)
   делится на клиузы по знакам «,» «;» «:» «—»; граница — в конце клиузы (знак входит
   в клиузу).
2. **Ранний запуск TTS.** Клиуза отправляется на синтез, как только накоплено ≥
   `MIN_CLAUSE_CHARS` (именованная константа, ~48 символов — «окно по длине»): синтез
   первой клиузы идёт параллельно с дальнейшей генерацией ответа LLM.
3. **Правило пауз** (между соседними частями — по завершайющему знаку предыдущей части):
   - «?» / «!» — пауза 500 мс;
   - «.» / «...» — пауза 250 мс;
   - «,» / «;» / «:» / «—» — пауза 0 мс (клиузы одной фразы играются подряд).

**Влияние на latency-бюджет.**
- Первый звук реплики ИИ наступает раньше на время генерации первой клиузы (не ждём
  целого предложения); межфразовые разрывы сокращаются.
- Порядок TTS-кадров и WS-контракт не меняются: кадры по-прежнему
  `{seq,flags}`+PCM16, нумерация seq непрерывна — клиент не меняется.

## Поправка (2026-10-09) — Silero VAD (onnx) в batch-пути вместо энергетического

**Статус:** принято (2026-10-09, T-20261008211334); реализовано в этой итерации.

**Мотив.** Batch-путь голосового конвейера — fallback, когда стриминговый STT
(`WS /stt/stream`, ADR-007) недоступен. Он детектирует реплики кандидата
**энергетическим VAD** в Go (`internal/vad`: RMS-порог + адаптивный шумовой пол).
Качество ниже Silero VAD: шум, дыхание и фон проходят как «речи» → ложные реплики →
STT-галлюцинации (фильтр `confidence ≥ 0.5` — костыль поверх, а не решение). Silero
VAD (onnx, ~2 МБ, MIT) уже работает в voice-сервисе для стримингового STT
(ADR-007, константы `VAD_THRESHOLD=0.5`, `VAD_MIN_SILENCE_MS=600`,
`VAD_MIN_SPEECH_MS=250`) — модель и инференс на месте.

**Ограничение сборки.** `CGO_ENABLED=0` — обязательное требование (Makefile, CI,
Dockerfile): бинарник static, переносимый, без нативных зависимостей. Вариант, нарушающий
его, допустим только с задокументированной поправкой сборки/CI.

**Сравнение вариантов.**

| # | Вариант | Зависимости | Размер/сборка | Latency | Риски | Итог |
|---|---------|-------------|---------------|---------|-------|------|
| 1 | onnx-инференс в Go (batch-путь api) | go-onnx-биндинги — cgo (`libonnxruntime`) | +~2 МБ onnx-модель + libonnxruntime; **ломает `CGO_ENABLED=0`** (нужен static-musl/динамический линк, поправка CI/Dockerfile) | без доп. сетевых хоппов (VAD+pre-STT вместе) | ломает обязательное `CGO_ENABLED=0`; портативность/размер бинарника; dlopen-неудачи на prod-узле | отклонён (только с поправкой сборки — не сто́ит риска) |
| 2 | **Перенос детекции в voice-сервис** (новый `WS /api/v1/vad/stream`) | **нет новых** (Silero onnx уже в voice, Python) | без изменений Go-бинарника (`CGO_ENABLED=0` сохранён) | +1 сетевой хопп (PCM-кадры → voice, state-события → api); voice в ЛВС, batch-путь уже ходит в voice (`/stt`, `/tts`) | voice и стриминговый STT на одном сервисе — если он лежит, срабатывает last-resort (вариант 3-й уровень) | **выбран** |
| 3 | Гибрид: Go держит state-машину, на каждое окно спрашивает voice prob | onnx уже в voice | без изменений бинарника | **×N сетевых хоппов** (по запросам на окно 32 мс) — latency детекции деградирует | недетерминированные задержки, потеря окон | отклонён (latency) |
| — | Оставить энергетический VAD | — | — | — | не решает ложные реплики (мотив задачи) | отклонён |

**Решение — вариант 2.**
1. **Новый endpoint voice:** `WS /api/v1/vad/stream` — клиент шлёт бинарные кадры
   PCM16 16 кГц mono; сервер (Silero VAD, per-connection clone, та же `StreamVAD`, что в
   `/stt/stream`) шлёт JSON-события: `state speech:true` (старт), `state speech:true
   pre_silence:true` (в речи, тишина ≥ `VAD_PRE_SILENCE_MS=400` мс — сигнал pre-STT, раз
   за реплику), `state speech:false` (конец: тишина ≥ `VAD_MIN_SILENCE_MS=600`, речь ≥
   `VAD_MIN_SPEECH_MS=250`). Без STT и partial (остаются в api/`/stt/stream`).
2. **api batch-путь — тонкий клиент.** `voicesvc.VADStream` (аналог `STTStream`): шлёт
   кадры, сам аккумулирует буфер реплики (pre-roll кольцо на старте слова), эмитит
   `speech_start`/`pre_silence(buf)`/`utterance(buf, speech_ms)`/`unavailable`. На
   `pre_silence` — pre-STT на текущий буфер (сохраняет выигрыш ~0.7 с); на `utterance` —
   barge-in-проверка + batch `POST /stt` (без изменений).
3. **Цепочка деградации (3 уровня):** (1) стриминговый STT (`/stt/stream`, Silero+STT);
   (2) Silero VAD stream (`/vad/stream`) + batch STT (`/stt`) — **новый уровень**;
   (3) энергетический VAD в Go (`internal/vad`) + batch STT — last-resort (сохранён).
   `internal/vad` не удаляется: остаётся офлайн-безопасной сетью безопасности и
   эталоном для A/B-замеров (без onnx).

**Константы** (voice, `stt_stream.py`): `VAD_THRESHOLD=0.5`, `VAD_MIN_SILENCE_MS=600`,
`VAD_MIN_SPEECH_MS=250`, новые `VAD_PRE_SILENCE_MS=400`.

**Влияние на latency-бюджет.**
- Конец реплики детектится раньше: тишина-порог 600 мс (Silero) против 900 мс
  (`EndSilenceMS` энергетического) — событие конца на ~300 мс быстрее.
- Pre-STT сохранён через событие `pre_silence` (400 мс) — не теряется выигрыш ~0.7 с.
- +1 сетевой хопп PCM→voice (кадры 250 мс, voice в ЛВС) — компенсирован более ранним
  концом; суммарный «конец речи → STT» не хуже (замеры — docs/test-results/).
- `CGO_ENABLED=0` и размер Go-бинарника **не меняются** (новостей в Go — только
  WS-клиент на `nhooyr.io/websocket`, уже в зависимостях).

## Поправка (2026-10-09) — Наблюдаемость barge-in: pre-roll-учёт и метрика speech_ms

**Статус:** принято (2026-10-09, T-20261009021739); реализовано в этой итерации.

**Контекст.** Риск из поправки 2026-10-09 (Silero VAD в batch-пути): pre-roll (до 1 с
тишины перед речью в pre-ring клиента `voicesvc.VADStream`) входит в длительность
реплики по байтам — короткая «реплика» (тишина + короткий всплеск) могла прерывать
TTS при реальной речи кандидата короче `BargeInMinSpeechMS=500` мс; метрика
`grade_barge_ins_total` не несла информации о длительности — риск было не наблюдать.

**Решение (вариант b — простой pre-roll-учёт).**
1. **Порог barge-in — по длительности речи (без pre-roll).** `VADStream` фиксирует
   `prerollB` — байты pre-ring, включённые в буфер при старте речи, и отдаёт их в
   `VADEvent.PreRollMS`; `completeUtterance(ws, utterance, prerollMS)` считает
   `ms = totalMS − prerollMS` и сравнивает с `BargeInMinSpeechMS` (порог 500 мс
   сохранён). Energy-путь передаёт `prerollMS=0` (в его реплику тишина не входит —
   поведение без изменений). Стрим-путь (`/stt/stream`) порога по буферу не имеет
   (timer 500 мс непрерывной речи + `speech_ms` из Silero VAD на voice) — не тронут.
2. **Метрика `grade_barge_in_speech_ms`** (histogram, мс, buckets 100/250/500/1000/
   2000/5000) — обсерв длительности речи при каждом barge-in во всех трёх точках
   (completeUtterance, streamBargeIn, handleSTTStreamFinal). Наблюдение: p50/p95
   устойчиво в 500–1000 мс — подозрение на ранние прерывания; доля
   `le="500"` > 0 — pre-roll-риск проявляется.
3. **Grafana** `infra/monitoring/grafana-dashboard.json` v2: row «Barge-in &
   Fallback» (rate/мин, доля ≤500 мс, fallback-счётчики, speech_ms p50/p95 с
   пороговой линией 500), row «Latency» (+ `grade_ai_tts_synth_seconds`), row
   «Health». Алертные пороги — docs/OPERATIONS.md.

**Known limitations (задокументированы, не чинятся в этой итерации).**
- **Race кадр-триггера:** client `VADStream` буферизует кадры локально, а состояние
  `inSpeech` обновляется по событию voice (сетевой RTT). Кадр-триггер `speech_start`
  (и в burst-режиме — до 3 последующих) попадает в pre-ring и вычитается как
  pre-roll → реальная длительность речи **занижается** на ≤ 3 кадра (750 мс).
  Направление безопасное (меньше ложных barge-in, но barge-in на короткой реальной
  речи может запаздывать); в реальном времени (кадры 250 мс) сдвиг ≤ 1 кадр.
- **Post-silence в буфере:** тише-кадры до события `pre_silence` (≤ ~400–500 мс)
  входят в буфер и НЕ вычитаются → `ms` может **завышаться** на величину
  post-silence. Чистая оценка речи по batch-пути возможна только с точностью
  ±(pre-roll race + post-silence); для точного значения — `speech_ms` voice
  (стрим-путь) или отдельная итерация.
- Burst-отправка кадров (клиент, держащий пакет, шлёт подряд) раздвигает lag
  ring/событий сильнее, чем в реальном времени — тот же known limitation, п. 1.
