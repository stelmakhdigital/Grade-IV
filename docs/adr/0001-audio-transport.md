# ADR-001. Транспорт аудио: WebSocket + аудио-кадры

**Статус:** принято (2026-09-09)

## Контекст
Кандидат общается с ИИ голосом в браузере (MVP — ходовой режим: кандидат говорит → ИИ
отвечает; barge-in вне скоупа, SRS §8). Нужен канал «микрофон → сервер (STT/LLM/TTS) → динамик».

## Решение
Один **WebSocket на сессию** (`/ws/session/{id}`, протокол — ARCHITECTURE.md v0.3, §4.2):
- **вверх**: аудио кандидата — сырые кадры **PCM16 16 кГц mono** (AudioWorklet-даунмикс,
  кадры ~250 мс) + текстовые события UI (`stage_action`, `whiteboard_saved`…);
- **вниз**: аудио ИИ — бинарные кадры **PCM16 16 кГц mono** (TTS, с 4-байтовым заголовком
  `{seq, flags}`) + JSON-события (`transcript`, `stage`, `ai_text`, `run_result`, `timer`,
  `report_ready`, `error`).

## Альтернативы
- **WebRTC**: ниже latency (~100–200 мс) и встроенный AEC, но требует SFU/media-инфраструктуры
  и не даёт преимущества в ходовом режиме (эхо-подавление не критично: ИИ молчит, пока
  говорит кандидат). Отклонено для MVP; путь апгрейда сохранён (та же семантика сессии).
- **Push-to-talk**: проще, но хуже UX — пользователь хочет «живой» диалог (решение #7).

## Последствия
- + Простота self-hosted: один лонг-коннект, стандартный websockets-стек FastAPI, нет media-сервера.
- + Лёгкий аудит и запись сессии (кадры проходят через сервер — транскрипт/аудио в истории).
- − Latency выше WebRTC на время накопления кадра (~0.25–0.5 с) — учтено в бюджете ADR-002.
- − Полоса PCM16 16 кГц mono ≈ 32 кбит/с — пренебрежимо мала.
- Апгрейд до WebRTC — замена транспорта, не протокола сессии (фаза Operations/A-B).
