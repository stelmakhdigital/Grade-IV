# ADR-009. Режим записи (FR-S8): накопление транскрипта без AI-ходов

**Статус:** принято (2026-10-09, T-20261009164629)

## Контекст
Живая сессия 2026-10-09: пользователь зафиксировал два бага/улучшения голосового
UX, решаемые единым механизмом:
1. Микрофон переинициализировался при каждом «выключить/включить»
   (getUserMedia → ожидание);
2. VAD закрывал реплику на каждой паузе ≥ 600 мс → каждый «затык» уходил
   отдельным ответом кандидата (AI-ход на каждый фрагмент).

Требование пользователя: пока включён микрофон — сервис **слушает и склеивает**
транскрипт (распознавание налёт), но отправляет как ответ кандидата **только
после «выключить микрофон»** (явная отправка). Оптимизация — длинные записи
(5–15+ мин).

## Решение

### WS-протокол (backward-compat: только добавления)
- C→S: `{"type":"ui","name":"recording","payload":{"on":true|false}}` — флаг
  режима на WS-сессии (`wsSession.recording`, сброс счётчика речи при on).
- S→C: `{"type":"stt_segment","text","speech_ms","total_speech_ms"}` —
  распознанный сегмент (final по тишине) в режиме записи. Старые клиенты
  игнорируют неизвестный type; старые серверы не шлют — совместимость.

### Сервер (api)
- Подавление хода — в двух точках сходимости (стрим-путь `runStreamTurn`,
  batch-путь `handleVoiceUtterance`), **после** фильтра доверия (conf < 0.5 —
  шум не попадает в транскрипт): вместо `runCandidateTurn` — `emitRecSegment`
  (stt_segment + накопитель `recSpeechMS`). Barge-in (tts_stop при ≥ 500 мс
  речи) работает как обычно — физика не меняется.
- Nudge не шлётся, пока `recording` (длинные паузы внутри записи — норма).
- Чанкование длинных записей: сегментация **по тишине уже есть** в
  /api/v1/stt/stream (Silero VAD, final по `VAD_MIN_SILENCE_MS`) — каждый
  final = сегмент, граница чанка — на тишине (не рвёт слова). Клиент держит
  только текст (KB), не аудио. **Жёсткий 30-с лимит** непрерывной речи
  (разрыв ultra-длинного speech-сегмента) — не реализован, в бэклоге.

### Клиент (frontend)
- `MicCapture`: `stop()` — **soft** (mute: `track.enabled=false`, поток/контекст
  живут, счётчики отладки сброс, нулевые чанки не шлются); `start()` по живому
  потоку — `enabled=true` за < 10 мс (без getUserMedia); мёртвый track
  (`readyState: ended`, событие `ended`) — полная инициализация (цепочка
  ADR-008 + лимит `MAX_REINIT`); `dispose()` — жёсткое освобождение (pause/
  unmount). ADR-008-цепочка (worklet→fallback→reinit) сохранена.
- `useVoiceSession`: режим записи активен, пока «включён микрофон»:
  `stt_partial` → `recPartial` (окно, не строки), `stt_segment` → `recSegs` +
  `total_speech_ms`. «Выключить микрофон» / «Отправить сейчас» (кнопка окна;
  после отправки микрофон выключается) → `recording off` + **одно**
  `utterance`-сообщение со склеенным текстом (`mergeRecording`: сегменты +
  хвост-интерим, WS-порядок: off раньше utterance) → AI-ход стартует.
  **Недостаточно речи** (пусто или `total_speech_ms < MIN_SPEECH_MS` = 1500) —
  не отправлять + заметка «Недостаточно речи…». Пауза сессии — запись
  сбрасывается (не переживает паузу), `dispose()` микрофона.
- Окно записи (voice-panel): живой склеенный транскрипт + «мм:сс» + статус,
  сворачивается.
- История диалога: `lines` хранятся как есть (append, кап 200), **рендер —
  новые сверху** (live/interim/REST-история — единый порядок), автоскролл
  контейнера к началу при новом сообщении, если пользователь у верхнего края
  (userNearTop < 80 px).

## Последствия
- + Конверсационный поток: кандидат говорит сколько нужно (5–15+ мин), ИИ
  отвечает на целую мысль, а не на фрагменты; «затыки» не засоряют диалог.
- + Переключение микрофона мгновенное (нет getUserMedia при каждом toggle).
- − Ходовой режим «реплика → немедленный ответ» заменён «запись → ответ»:
  диалог становится push-подобным (кандидат управляет границами ходов).
  Это **решение пользователя** (2026-10-09) — основной сценарий сервиса.
- − known: (a) жёсткий 30-с лимит непрерывной речи — backlog; (b) хвост
  записи < 600 мс тишины до off не становится сегментом — клиент склеивает его
  из recPartial (live-проверка 2026-10-09, ограничение 2); (c) STT может терять
  стартовые слова фразы на границе сегмента (поведение ADR-007, не режима).

## Альтернативы
- **Клиентская VAD-сегментация** (аудио-буфер в браузере): отклонено — память
  (5–15 мин PCM = 30–75 МБ) и дублирование VAD-логики; серверный STT-стрим
  уже сегментирует по тишине (ADR-007).
- **Отдельная «режим-записи» сессия/эндпоинт**: отклонено — flag на WS +
  существующие пути (стt-стрим/ utterance-канал) достаточно, backward-compat
  сохраняется.
- **Автоматическая отправка по длинной тишине** (напр. 10 с): отклонено —
  против прямого требования («только после выключить микрофон»).
