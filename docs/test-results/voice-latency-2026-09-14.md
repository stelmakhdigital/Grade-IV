# Голосовой контур: latency и качество STT — 2026-09-14

**Задача Фазы 4** (TEST_PLAN §3). Живой контур: api (LLM_MOCK, VAD 900 мс) →
voice (faster-whisper CPU + Silero v5) → WS. Методика: `services/voice/latency/probe.py`
(WS-клиент: фразы эталона синтезируются Silero TTS (24 кГц), ресемплингуется в
16 кГц (контракт WS, ADR-001), шлётся чанками 250 мс с непрерывным «микрофоном»
(речь + 12 кадров тишины — VAD ждёт EndSilenceMS в потоке); до отправки — ожидание
конца TTS-приветствия по flag 0x0001 — turn-taking).

**Эталон:** 20 фраз (dev-речь кандидата, 2–3.3 с), `services/voice/latency/etalon20.json`.
Синтетическая речь (Silero eugene) — верхняя граница качества; живая речь будет хуже.

## Замеры (CPU, 20 прогонов/модель)

| Метрика | tiny (int8) | small (int8) | Цель (TEST_PLAN) |
|---|---|---|---|
| stt p50 / p95 (от начала отправки) | 5.76 / 6.52 с | 5.76 / 6.52 с | p95 < ~2.5 с до STT-результата* |
| tts-старт p50 / p95 | 5.76 / 6.53 с | 5.76 / 6.52 с | p95 < ~4 с (с LLM-моком) |
| Качество STT (среднее сходство, Левенштейн) | 0.68 | **0.87** | ≥ 0.85 |

*Разбивка p50 (фраза ~2 с): конец реплики VAD ≈ 2 + 0.9 = 2.9 с + распознавание
whisper int8 CPU ≈ 2.3–3.2 с (зависит от длины реплики, p95 — на фразе 3.3 с).
LLM-ответ (мок) — мгновенно; TTS-старт (Silero, CPU, короткая реплика) — +<0.1 с.

## Выводы

1. **Конвейер работает сквозным**: 20/20 фраз — VAD → STT → LLM → TTS, без потерь
   ходов, turn-taking соблюдается (пробер ждёт конца приветствия).
2. **Качество STT**: tiny — 0.68 (ниже порога 0.85), small — 0.87 (порог пройден
   в 18/20, провалы 0.62–0.73 — фразы с терминологией: Prometheus/Kafka/JWT,
   «код-ревью», «облако»). Рекомендация для prod: **small на CPU** (MVP) и
   **large-v3 на GPU** (SRS) — ожидается рост качества на 0.9+; дефолт
   `.env.example` (STT_MODEL=small) подтверждён.
3. **Latency (уточнено глубинным замером, 2026-09-14 вечером)**: метрика
   «stt_s» в таблице = конец реплики + VAD-хвост + распознавание, где:
   - VAD-хвост 0.9 с — **проектное** (end-of-speech detection; без него ИИ
     обрывал бы реплику на паузах — компромисс SRS §8);
   - STT (whisper small int8, 2 с аудио) — **0.68 с** (бенч; beam/vad_filter
     не дают выигрыша: 0.6–0.7 с во всех комбинациях);
   - длительность самой реплики (1.5–3.3 с) — в метрике, но не «доля системы»;
   - api→клиент — **миллисекунды**: прямой замер text-utterance 3 мс;
     таймер-конфликт на connMu **исключён** (реверс эксперимента не дал
     эффекта; conn.Write блокирует только на TCP-окне).
   **Итог: пайплайн VAD→STT→LLM→TTS добавляет ~1.6–2.2 с к окончанию речи
   кандидата. «До TTS-старта» = речь + 0.9 + 0.7 + LLM (1–3 с с Qwen3.8-27B) —
   SLO p95 <4 с достигается только со стриминговым STT (chunked) или
   EndSilence 700 мс (риск обрывов) — оба в бэклоге (ADR-002-обновление).
   Подводный камень замера: WS-клиент без параллельного read-pump «зависает»
   в TCP-буфере (артефакт проба, не системы) — реальные клиенты читают
   постоянно.
4. ТТS (Silero v5 CPU) — не узкое место для коротких реплик (<0.5 с синтеза).

## Данные

- `voice-latency-2026-09-14-tiny.json`, `voice-latency-2026-09-14-small.json`
  (пофразные stt/llm/tts-таймстампы + распознанные тексты).
- Стек замера: api `grade-apil4` (LLM_MOCK=1, VAD_END_SILENCE_MS=900,
  VAD_RMS_THRESHOLD=500, SILENCE_NUDGE_S=30, :8900); voice :8100 (tiny) /
  :8101 (small); probe — `services/voice/latency/probe.py`
  (`--api --tts --runs --out`).

## Ограничения

- Синтетическая речь, один спикер; живая речь (шум, темп) — ниже качество.
- LLM-мок — реальный Qwen3.8-27B добавит 1–3 с к latency ответа (не к старту TTS
  первой реплики — она уже учтена в SLO-цели).
- CPU-замер (нет GPU-узла в окне Фазы 4, TEST_PLAN §7.1) — GPU-конфигурация
  остаётся бэклогом (large-v3 + стриминг).
- Побочные находки: (a) `LOG_LEVEL` читается из окружения, но не применяется к
  логгеру (debug-логи не пишутся) — баг, бэклог; (b) TTS-кадры api шлёт burst'ом
  (без real-time pacing) — на фронте воспроизведение корректное, для стриминга
  TTS (бэклог) потребует pacing.

# Load-тест real-time (TEST_PLAN §5) — 2026-09-14

**Сценарий** (`services/api/internal/httpapi/load_test.go`,
TestLoadWS50Sessions): 50 одновременных WS-голосовых сессий (in-process
server, LLM-мок), каждая 20 с: непрерывная отправка PCM-чанков 250 мс
(синус 440 Гц, амплитуда 8000 — VAD реально обрабатывает каждый кадр),
приём timer/ai-сообщений. Нагрузка: WS-транспорт ×50, VAD ×50, движок
сессий (тик-цикл), nudge-циклы ×50, SQLite (persist active-seconds).

| Метрика | Результат | Цель (TEST_PLAN §5) |
|---|---|---|
| Сессии до конца | 50/50 (20 с каждая, без срывов) | без обрывов |
| Таймер-тики | 200 (по 4 на 20 с, period 5 с — без срывов и дублей) | p95 tick ≤ 1 с (дрейф не обнаружен) |
| Клиентских error-сообщений | 0 | 0 |
| Время прогона | 20.2 с wall (50 параллельно) | — |

**Вывод**: MVP-нагрузка (50 голосовых сессий на одном api-процессе, CPU)
выдерживается с запасом; узких мест по таймеру и транспорту не обнаружено.
Ограничения: voice-контур в load не участвует (STT/TTS — CPU-узкое место,
см. latency-отчёт выше); нагрузочный тест с реальным STT — на GPU-узле (бэклог).

**Инструмент**: go test (детерминирован, входит в `make test`); к6-вариант
для REST (регистрация/сессии) — не требовался (REST-нагрузка на порядки
ниже WS-реального времени).
