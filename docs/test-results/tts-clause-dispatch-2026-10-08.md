# TTS pacing: межфразовые разрывы 750–1500 мс — клиуза-уровневая диспетчизация (A/B)

- Дата: 2026-10-08; ветка `agent/backend/1` (база — `4a6e048`).
- Задача: T-20261008185701 (приоритет 3). Контекст: `docs/test-results/voice-latency-2026-09-14.md`, PROJECT_MEMORY решение #36.

## Что менялось

Клиуза-уровневая диспетчизация TTS в `services/api` (Go), `internal/httpapi/voice_pipeline.go`:

1. `MIN_CLAUSE_CHARS = 48` — минимальная длина части (байты) для дробления на клиузы;
   короткие предложения уходят в TTS целиком.
2. `splitForTTSStreaming(text) → (части, хвост)` + `splitClausesWithTail`: предложение
   (логика `splitSentences` без изменений) дополнительно делится на клиузы по границам
   «,» «;» «:» «—» (граница остаётся в конце клиузы, завершитель предложения — в
   последнем клиузе), если часть ≥ 48 байт. «:» внутри чисел («12:30») не дробит;
   фрагмент из одних знаков («—») отдельной частью не отправляется.
   Открытый хвост возвращается **raw (без обрезки)** — `splitDeltas` приписывает к нему
   токены (обрезка склеивала слова: «Отвечу» + «коротко » → «Отвечукоротко» —
   потенциальный дефект, обнаруженный и устранённый в ходе задачи).
3. `splitDeltas` диспетчизует через `splitForTTSStreaming`: готовая клиуза уезжает в
   TTS-канал, когда после неё начинается следующая (не нужно ждать конца предложения).
4. Правило пауз `ttsGap(prev)` (в `produceOrderedTTS` и `streamAIAudio`) по
   завершайющему знаку предыдущей части: «?/!» → 2 тише-кадра (500 мс),
   «.»/«...» → 1 (250 мс), «,»/«;»/«:»/«—» → **0** (клиузы одной фразы играют подряд).
5. `llm/mock.go` (тесты): `SetTokenDelay(d)` — задержка между токенами в
   ChatStream-стриме (по умолчанию 0 — весь ответ одним токеном, как раньше);
   `StreamEnd()` — момент окончания последней поставки стрима.

WS-контракт кадров (4B LE, 250 мс, bit0 end) и REST не менялись. Внешних зависимостей
нет. `services/frontend|voice|infra` не тронуты.

## Детерминированный тест (доказывает механизм)

`TestClauseDispatchEarlyTTS` (`internal/httpapi/voice_pipeline_test.go`): мок-LLM
стримит фиксированный сценарий с управляемой задержкой 100 мс/токен: короткое
предложение 1 («.», 39 байт) + предложение 2, первый клиуз (123 байта ≥ 48)
заканчивается «,» на ~17 токене, всё предложение — на ~27 токене.

Результат (проход):
- (а) TTS-вызов с текстом первого клиуза (оканчивается «,») выполнен за **1.00 с до
  конца LLM-стрима** (ранняя диспетчизация сработала);
- (б) между PCM-кадрами клиуз одной фразы тише-кадров нет (gap=0);
- (в) после «.»-предложения тише-пауза 1 кадр (250 мс) сохранена.

Юнит: `TestSplitForTTS` (короткая часть без дробления; клиузы по «,» «;» «:» «—»;
граница в конце клиузы, завершитель — в последнем; «12:30» не дробится; пустые/
пробельные без артефактов), `TestTTSGap` (таблица значений пауз).

Регресс: все тесты api зелёные (`go test ./...`, 7 pkgs; `go vet` OK; `gofmt -l` пусто).
Одно арифметическое ожидание в `TestBargeIn_ShortUtteranceDoesNotInterrupt` обновлено:
мок-ответ (71 байт ≥ 48) теперь дробится на 2 клиузы → 24 кадров вместо 12; сценарий
barge-in (короткий burst не прерывает, стрим доигран полностью) не менялся.

### Интерпретация (честно)

- **first_tts**: среднее 1699 → 1638 мс (−61 мс, ~−4%); разброс внутри бинарника
  (1564–1781 мс) больше разницы — статистически «не ухудшилось», лёгкое улучшение в
  пределах шума. first_tts в основном определяется prefill/первыми токенами LLM
  (~1.6–1.8 с) — на него клиуза-диспетчизация влияет минимально.
- **Межфразовые разрывы**: по 3 ранам на бинарник суммарно 19500 → 19250 мс (−1.3%),
  количество 18 → 18. **Live-эффект не выделился из шума**: LLM недетерминирован
  (ответы разные: и по длине, и по пунктуации), часть ответов состоит из коротких
  предложений (< 48 байт), которые клиузами не дробятся; остаточные разрывы 1000–1500 мс
  — это моменты, когда очередь TTS опустела и ждалась генерация следующей части LLM
  (~10–25 ток/с) — клиуза-дробление сокращает, но не устраняет ожидание.
- **Вывод**: регрессии нет (first_tts и разрывы в пределах шума, кадры те же порядки);
  механизм раннего запуска TTS на клиузе доказан детерминированным тестом
  (запас 1.0 с до конца стрима) и юнитами. Реальный выигрыш в live растёт с длиной
  предложений в ответах LLM; для измерения его в стабильных условиях нужен прогон
  с фиксированными (seed/few-shot) ответами LLM — не сделано в рамках задачи.

## Ограничения

- LLM-уз общий и недетерминированный: 3 рана на бинарник — малая выборка, ответы
  различаются; A/B показывает «без регрессии», а не величину выигрыша.
- Разрывы мерятся пробой как серии тихих 250-мс кадров (rms < 300) > 500 мс;
  естественные паузы TTS (Silero) внутри фразы в них не попадают.
- После замеров оба api убиты, `git worktree /tmp/grade-ab-old` удалён, порты
  8002/8003 свободны; чужой стек (:8000/:5173/:8100/:8200) не тронут.
